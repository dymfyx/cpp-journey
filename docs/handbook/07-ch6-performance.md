# 第 6 章 性能：从「感觉快」到「数字说明快」

> 这一章来自第 7 周的 `std::to_chars` 优化：Dump/Compact 从 162 MiB/s 提到 246 MiB/s，并且搞清楚了「为什么快」。核心原则：**先测量，再优化；每次只改一个变量，用同一会话的前后对比。**

## Q6.1 基准测试的纪律

**疑问**：为什么同一个程序跑两次，数字差 40%？

**解答**：笔记本/WSL2 上数字波动的来源：

| 来源 | 影响 |
|---|---|
| CPU 频率（睿频/降频） | 同代码跨会话差 30–40% |
| 后台进程（VS Code、浏览器、微信） | 抢占 CPU、抢内存带宽 |
| 内存压力/swap | 大文档基准明显变慢 |
| 系统 `libbenchmark` 是 Debug 构建 | 绝对数字整体偏高（日志有 WARNING） |
| 单轮 vs 多轮 | 单轮随机性大，中位数更稳 |

**纪律**：

1. 只做**同一次会话内**的前后对比；
2. 至少 `--benchmark_repetitions=5`，报 **median**；
3. 看 **cv**（变异系数），>5% 时不要下结论；
4. 记录构建类型（Debug/Release、是否 -O3、是否 sanitizer）。
5. 两次测量差异 <10% 视为「无变化」。

**一句话**：不能重复测量的「快」都是玄学。

**项目里**：README 性能表标注「Ubuntu 24.04 / g++ 13.3 / -O3 / 中位数 / 1MB 文档」。

## Q6.2 优化顺序：先找热点，再改

**疑问**：怎么知道该优化哪里？

**解答**：用工具的层次：

```
1. 先看算法复杂度（O(n) 还是 O(n²)）        ← 最大收益
2. 再看热点（perf/benchmark 分解）           ← 第二
3. 最后看指令级（cache、分支、SIMD）          ← 第三
```

本项目 dump 的热点就是「每个数字一次 `snprintf`」，占了大部分时间——这靠读代码 + 对比 nlohmann 的数字推断出来的，然后用 benchmark 验证。

**一句话**：先改「做不做」和「做几次」，再改「做得快不快」。

**项目里**：`src/value.cpp` 的 Number 分支；`docs/design.md` 第 5 节。

## Q6.3 `snprintf` 为什么慢

**疑问**：`snprintf` 才一个函数调用，能有多慢？

**解答**：慢在四层：

1. **格式串解析**：`"%.17g"` 在运行时解析（不是编译期常量）；
2. **locale 查询**：`printf` 系列受 `LC_NUMERIC` 影响（某些 locale 用逗号做小数点），每次要查/加锁；
3. **通用大数路径**：glibc 的 `printf_fp` 用任意精度大整数做精确舍入，可能 `malloc`；
4. **写缓冲区 + 返回长度**：还要处理宽度/精度参数。

而 `std::to_chars`：

- 类型在编译期确定（`double` 重载）；
- 标准规定**与 locale 无关**；
- 写入调用者给的 buffer，**不分配**、不写 `\0`；
- libstdc++ 用 Ryu 类算法（见 Q6.4），可内联。

**一句话**：`snprintf` 是「通用工具箱」，`to_chars` 是「专用工具」；专用快 2–5 倍很正常。

**项目里**：第 7 周实测 Dump/Compact 162→246 MiB/s（约 +50%）。

## Q6.4 Ryu 算法（最短往返浮点打印）

**疑问**：`0.1` 只有 3 个字符，为什么打印一个 double 需要复杂算法？

**解答**：目标不是「精确」，而是「**最短的、能读回同一个 double 的十进制表示**」。Ryu 的四个步骤：

1. **拆分**：double = `m × 2^e`（m 是 53 位尾数）；
2. **确定舍入区间**：`[vm, vr, vp]`（下界、值、上界），端点归属取决于 m 的奇偶（偶数时区间闭合，保证唯一性）；
3. **128 位乘法**：用预计算的 `pow5` / `pow5_inv` 表（约 326 + 342 条，10–11KB）做 `m × 5^k` 的 128 位乘 + 移位，得到候选十进制数；
4. **去尾循环**：`while (vp / 10 > vm / 10) { vp /= 10; vr /= 10; vm /= 10; }` 保证「最短」，再做边界修正。

对比其他算法：

| 算法 | 特点 |
|---|---|
| `printf`（精确） | 精确但慢，可能大数分配 |
| Grisu2 | 快，但有回退路径（可能不走最短） |
| **Ryu** | 快且保证最短，无回退 |
| Dragonbox | 表更紧凑，速度相当（nlohmann 用它） |

**一句话**：Ryu 用「预计算表 + 128 位乘 + 区间判定」找到最短往返表示。

**项目里**：`std::to_chars` 的 libstdc++ 实现；解释见 `docs/design.md` 第 5 节。

## Q6.5 内存带宽与缓存

**疑问**：为什么 1MB 文档的解析速度是 133 MiB/s，而小文档是 325 MiB/s？

**解答**：大文档要访问主存、缓存不命中多：

- 1MB 输入 + 解析后的 DOM（可能 3–5 倍放大）→ 远超 L2（1–2MB）、接近 L3；
- 每一步字符读取、vector 扩容、map 节点插入都会访问不同内存区域；
- 小文档（80B）全在 L1 里，只有固定开销。

优化方向：减少分配（预分配 vector）、减少拷贝（`string_view`）、改善局部性（DOM 连续存储），都是第 8 周以后的事。

**一句话**：小文档看固定开销，大文档看内存带宽。

**项目里**：`benchmark/bench_parser.cpp` 的 Tiny/Large 两个用例。

## Q6.6 基准命名与过滤

**疑问**：`Parse/Large`、`Dump/Compact` 这些名字哪来的？

**解答**：`BENCHMARK(函数)->Name(...)` 或直接 `BENCHMARK(函数)` 生成「函数名」；用 `->Arg()` 会追加参数。本项目用「操作/场景」命名：

| 名字 | 调用 | 输入 |
|---|---|---|
| `Parse/Tiny` | `jq::parse(tiny_doc)` | 80B |
| `Parse/Large` | `jq::parse(large_doc)` | 1MB |
| `Dump/Compact` | `v.dump(-1)` | 1MB DOM |
| `Dump/Pretty` | `v.dump(2)` | 1MB DOM |
| `EvaluatePath/Large` | `evaluate_path(v, ".records[1000].name")` | 1MB DOM |

过滤：`--benchmark_filter='Dump'`（子串/正则）、`'Parse/Large'`（精确）。

**一句话**：名字是给人看的 API；场景分得越清，结论越有意义。

**项目里**：`benchmark/bench_parser.cpp`。

## Q6.7 与 nlohmann/json 对拍

**疑问**：为什么这个项目要和别的库比？

**解答**：对拍（differential benchmarking）是证明「不是玩具」的最低成本方式：

- 相同的 1MB 文档（`benchmark/doc_gen.hpp` 两边共享，保证逐字节一致）；
- 相同的操作（parse / dump / dump(2)）；
- 同一台机器、同一会话、各 5–10 轮取中位数。

实测（第 7 周后）：

| 操作 | jq-lite | nlohmann/json | 结论 |
|---|---|---|---|
| Parse/Tiny | 190 ns | 583 ns | 快 3.0×（递归下降、无 SAX 中间层） |
| Parse/Large | 133.9 MiB/s | 63.9 MiB/s | 快 2.1× |
| Dump/Compact | 245.8 MiB/s | 240.2 MiB/s | 相当（to_chars 后追平） |
| Dump/Pretty | 162.5 MiB/s | 173.4 MiB/s | 慢 6%（缩进逻辑还需优化） |

诚实的结论比「我全都快」更有价值。

**一句话**：对拍的意义是「同输入、同操作、同机器」下的相对数字。

**项目里**：`benchmark/bench_nlohmann.cpp`；README 对比表。

## Q6.8 什么时候不优化

**疑问**：性能优化有尽头吗？

**解答**：三条止损线：

1. **满足需求就停**：1MB/5ms 够用，不要为了 +10% 把代码写复杂；
2. **可读性优先**：`std::map` vs `unordered_map` 的 O(log n) 在几十个 key 上无关紧要，但输出稳定性很重要；
3. **别优化没测量的代码**：先 profile，再动手；改完必须重新测。

**一句话**：优化的目标是「达成指标」，不是「追求极限」。

**项目里**：第 7 周只改数字格式化（热点），没动解析器（已经比 nlohmann 快）。
