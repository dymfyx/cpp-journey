# 第 7 章 学习方法与元认知

> 这一章不是技术，但决定了技术能走多远。记录的是我在这个项目里踩过的「学习方式」的坑。

## Q7.1 为什么「先讲函数再让我写」比「先写再讲」有效

**现象**：我写过一版 `create_pair`，能跑，但说不出 `socketpair` 和 `socket` 的区别、为什么需要 `SOCK_CLOEXEC`。逐行看代码时才发现自己只是照着抄。

**根因**：没有「心智模型」就动手，写出来的是**模式匹配**（见过类似的就改改），不是**理解**（知道为什么这样设计）。

**对策（教学协议）**：每个新函数先过「预习卡」：

1. 它是干什么的（一句话）；
2. 概念地图（和谁配合、在流程的哪一步）；
3. API 速览（参数、返回值、错误）；
4. 心智模型（内核里发生了什么）；
5. 常见坑；
6. 深读资料（man page、书章节）。

然后我再写、再 review。**先建图，再填细节。**

**证据**：`create_tcp` 先讲后写一次通过；`bind/listen` 直接给代码时，我写了三版才对。

## Q7.2 从 OI 到工程：三个思维转变

| OI 习惯 | 工程习惯 |
|---|---|
| 程序 = 输入 → 算法 → 输出 | 程序 = 一堆对象 + 生命周期 + 错误路径 |
| 全局数组、手动 memset | RAII、所有权、禁止裸 new/delete |
| 一次跑对就行 | 可测试、可复现、可 benchmark、可安装 |
| 只看 WA/TLE | 看 ASan 报告、看 P99、看 CI 红绿 |
| 一个人写 | 写给别人看（README、design.md、commit message） |

**一句话**：OI 训练「写出正确的一次性程序」，工程训练「交付可维护的软件」。

## Q7.3 怎么提问才学得动

**现象**：我早期的提问是「这段代码怎么写」「这个报错怎么修」。

**问题**：这类问题得到的是**答案**，不是**能力**；下次遇到同类问题还是要问。

**改进后的提问模板**：

1. 我观察到什么（报错/现象/代码片段）；
2. 我猜原因是什么；
3. 我试过什么；
4. 我卡在哪一步。

例：

> 「`ctest` 报 `DumpNumbers` 失败，期望 `0.1` 实际 `0.10000000000000001`，我猜是数字格式化问题，查了 `%.17g` 的语义，但不确定 `to_chars` 默认格式是什么——这两个的取舍是什么？」

这类问题我得到了「原理 + 取舍 + 延伸」，而不是「把第 37 行改成 X」。

**一句话**：问「为什么/怎么权衡」，别只问「怎么写」。

## Q7.4 输出倒逼输入

**现象**：学完一周，觉得「都懂了」，但讲不出来。

**对策**：三个输出物：

1. `docs/HANDOFF.md`：给下一个 AI/下一个人看的进度交接（环境、协议、坑、待办）；
2. `docs/design.md`：给面试官/同事看的取舍说明（为什么 `map`、为什么 512、为什么 `to_chars`）；
3. 本书（复盘手册）：给未来的自己看的系统总结。

写不出来 = 没真懂。写的过程会逼你补上「我大概知道」的漏洞。

**一句话**：能讲清楚才算学会；输出是最好的复习。

## Q7.5 节奏：每周 8–10 小时的排法

**现象**：有几天一口气学 6 小时，然后两天不想碰。

**问题**：工程学习是**累积**的，断档后要重新捡上下文（我每次「两天没看」都要先回顾进度）。

**对策**：

- 每周 8–10 小时，拆成 4 次 × 2 小时（比一次 8 小时有效）；
- 每次结束前留 10 分钟写「下次从哪开始」（HANDOFF 的用途）；
- 考试周允许降速，但保持「每周至少一次 commit」；
- 大块时间用来写代码，碎片时间用来看概念/读文档。

**一句话**：稳定的小步 > 间歇的大步；留好「重启锚点」。

## Q7.6 怎么读开源代码

**方法**（以 nlohmann/json 和 muduo 为例）：

1. **先看 README 和示例**：它解决什么问题、怎么用；
2. **看目录结构**：头文件 / 实现 / 测试 / 文档；
3. **从入口追调用链**：`parse` → 词法 → 语法 → DOM，只追一条线；
4. **看测试和 benchmark**：它怎么验证正确性、怎么测性能；
5. **不追求全懂**：只在需要时深挖某一模块。

**反面教材**：从第一个文件开始逐行读，读到第 300 行放弃。

**一句话**：带着问题读代码，从入口和测试切入，不求全。

## Q7.7 调试思维：二分与最小复现

**现象**：程序崩溃，看着 200 行代码不知道哪错。

**方法**：

1. **最小复现**：把输入缩到最小（`[`、`{`、`"`），去掉无关代码；
2. **二分**：注释一半代码/删一半输入，看问题是否还在；
3. **二分删代码**：从能崩的版本开始，删到不能再删（我删边界检查的实验就是这样定位到 `take` 的越界）；
4. **对照实验**：改一个变量，观察一个指标（比如三构建对比：Release / Debug+ASan / Debug）。

**一句话**：调试 = 缩小可疑范围，不是盯着代码看。

## Q7.8 AI 使用的边界

**现象**：让 AI 直接生成整段实现，代码能跑，但过两周忘了。

**原则**（本书遵循的）：

- 核心实现**自己写**，AI 只给骨架、接口、评审、解释；
- 卡住超过 20 分钟再要提示，要「方向」不是「答案」；
- 每段 AI 解释都要能在项目里指出对应位置和测试；
- 重要结论写进 HANDOFF/design（否则下次还要问）。

**一句话**：AI 是加速器不是替代品；**能复述、能改、能讲**才算掌握。
