# 第 8 章 我主动补的深层问题

> 这一章不是「我问过的问题」，而是**你还没意识到、但会卡住你三年的问题**。每一条都给了「现象 / 根因 / 对策 / 本项目的证据」。

## 8.1 懂语法，不懂「模型」

**现象**：能写出 `std::variant`、`std::map` 的代码，但被问「这个对象在内存里长什么样」就答不上来。

**根因**：语法是「怎么写」，模型是「运行时发生了什么」。只学语法，遇到性能、调试、ABI、模板错误就会卡住。

**对策**：

1. 每学一个类型，问三个问题：占多少字节？拷贝时发生什么？析构时发生什么？
2. 用 `sizeof`、`typeid`、汇编、ASan 实验验证；
3. 画图：对象布局、虚表、栈帧。

**本项目证据**：`sizeof(jq::Value) == 56` 的推导；`std::string` 32 字节与 SSO；`Buffer` 对象在栈、`data_` 在堆。

## 8.2 调试工具缺失

**现象**：程序崩了就 `printf` 大法，找不到就越改越乱。

**根因**：没建立「症状 → 工具」的映射；不知道 ASan 报错怎么读。

**对策**：

- 常备四个工具：ASan 构建、gdb、strace、perf；
- 读 ASan 报告三要素：错误类型、位置、变量来源（栈/堆/全局）；
- 学会最小复现与二分（见 7.7）。

**本项目证据**：删边界检查后 ASan 报 `stack-buffer-overflow in take()`，直接定位到 `parse_string` 越界；gdb `bt` 抓过测试崩溃调用链。

## 8.3 理论滞后于实践

**现象**：能写 epoll 服务器，但说不清「为什么 LT 和 ET 的语义不同」；能用 CMake 安装，但说不清「为什么需要 export」。

**根因**：工程学习以「能跑」为标准，理论课（OS、编译原理、体系结构）被当成「以后再补」。

**对策**：

- 每完成一个项目，补一章对应理论（epoll ↔ OS 的 IO 多路复用；CMake export ↔ 链接与包管理）；
- 用「面试问题」自测理论：能不能用 3 分钟讲清？

**本项目证据**：`docs/design.md` 每节都回答「为什么」，而不只是「是什么」。

## 8.4 错误处理策略没有建立

**现象**：同一个项目里三种错误处理混用——异常、错误码、`assert`，接口不一致。

**根因**：没人教过「什么时候用哪种」，凭感觉。

**对策（本项目最终采用的策略）**：

| 场景 | 方式 |
|---|---|
| 可预期、调用方必须处理 | 异常（`ParseError`、`QueryError`） |
| 库边界/性能敏感 | 返回 `optional`/`expected`（本项目未用，保持异常一致） |
| 程序 bug（不变量被破坏） | `assert` |
| 不可恢复 | 直接 `abort`/`std::terminate` |

并在文档里写清楚（design.md 第 7 节「已知限制」）。

**一句话**：错误处理是接口设计的一部分，必须先定策略再写代码。

## 8.5 项目叙事能力

**现象**：面试官问「你这个项目最难的地方是什么」，答「就是写了个 JSON 解析器」。

**根因**：只记「做了什么」，不记「为什么这样做、怎么验证、踩过什么」。

**对策**：每个项目准备三段：

1. **为什么做**（解决什么问题，替代方案是什么）；
2. **最难的点**（举一个具体 bug/取舍，讲清怎么发现、怎么解决）；
3. **怎么证明**（测试数字、benchmark、CI、与同类对比）。

**本项目证据**：README 的「设计取舍」「性能」两节、`docs/design.md`、本书。

## 8.6 依赖 AI 的风险

**现象**：让 AI 写完，测试过了，但自己删掉重写写不出来。

**根因**：AI 给的是「结果」，学习需要的是「过程」。

**对策**：本书第 7.8 节的三条边界；另外加一条：**每次 AI 给完整实现，必须做一次「闭卷复述 + 改一处 + 讲给空气」**。

**本项目证据**：`value.cpp` 重写（我写了 200 行后要求清空重写）；`min_bench` 手写（而不是直接复制 `bench_parser.cpp`）。

## 8.7 节奏：总想「一口气做完」

**现象**：计划 10 周的项目，前两周冲太猛，第三周开始拖延。

**根因**：把学习当冲刺，没有可持续的节奏和反馈。

**对策**：见 7.5；另外用「每周一个可交付物」替代「每周学完一章」——交付物能 commit、能展示、有成就感。

**本项目证据**：仓库 20+ 个 commit，每个都是一周内的可交付增量（骨架 → 单测 → 功能 → 测试 → 文档）。

## 8.8 输出不足

**现象**：学了很多，简历上写不出三行。

**根因**：输入（看/写）很多，输出（总结/讲给别人/写文档）很少。

**对策**：

- 每个阶段结束写一篇「我学会了什么 + 数字 + 坑」；
- 把讲解写成文档（本书就是）；
- 半年复盘一次：哪些真的会了，哪些只是见过。

**本项目证据**：本书 + `docs/design.md` + `docs/HANDOFF.md` + README。

## 8.9 补充：三个「现在就该知道」的边界

1. **测试覆盖率不是目的**：68 个测试的价值在「关键路径 + 边界」，不是行数；
2. **性能优化要有止损线**：满足指标就停，别为 5% 牺牲可读性；
3. **知识库不是收藏夹**：存进去的东西必须被读过、用过，否则只是焦虑的来源。
